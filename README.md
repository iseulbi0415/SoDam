역류성 식도염(위식도역류질환, GERD)이 있는 사람이 **"이 끼니를 먹었으면 몇 시간을
기다려야 하는가"**를 판단할 수 있게 돕던 iOS 앱입니다.

명지대학교 제5회 창의적 SW프로그램 경진대회 출품작(2026)이며, 현재는 운영을
종료하고 포트폴리오로 남겨두었습니다 — 자세한 배경은 이 문서 맨 아래
["현재 상태"](#현재-상태)를 참고해 주세요.

임상 가이드라인은 "취침 2~3시간 전 식사를 피하라"는 **범위**만 제시하고, 샐러드를
먹었을 때와 삼겹살을 먹었을 때 어느 쪽을 적용해야 하는지는 알려주지 않습니다.
이 앱은 **그 판단을 끼니의 총 지방량으로 자동화**했습니다.

## 핵심 기능 — 소화 안심 타이머

끼니에 포함된 **모든 음식의 지방량을 합산**해 대기 시간을 차등 적용합니다.

| 끼니 총 지방량 | 타이머 | 근거 |
|---|---|---|
| 10g 미만 | 2시간 | ACG 가이드라인 권고 범위의 하한 |
| 10g 이상 ~ 25g 이하 | 3시간 | 권고 범위의 상한 |
| 25g 초과 | 4시간 | 고형식 90%가 위를 빠져나가는 데 걸리는 시간 |

임상 가이드라인(ACG)이 제시하는 "취침 2~3시간 전"이라는 **범위**를 그대로 쓰지 않고,
그 범위의 하한·상한을 끼니의 지방량에 따라 나누어 배분했습니다. 지방이 특히 많은
끼니는 위 배출 연구가 말하는 4시간까지 늘립니다. 새로운 기준을 만든 게 아니라,
기존 권고를 한 끼 단위로 배분하는 규칙을 설계한 것입니다.

**설계상 특징 세 가지**

- **끼니 단위 합산** — 개별 음식이 아니라 그 끼니 전체를 봅니다. 같은 음식도 수량이
  늘면 구간이 올라갑니다. (곱창 1개 → 2시간 / 2개 → 3시간)

- **안전 마진 규칙** — 타이머가 이미 동작 중일 때 새로 계산된 시간이 남은 시간보다
  짧으면 무시하고 긴 쪽을 유지합니다. **값이 짧아지는 방향의 갱신은 허용하지 않습니다.**
  가벼운 음식을 나중에 먹었다고 해서 앞서 먹은 기름진 음식이 소화된 것은 아니기 때문입니다.

- **사용자 개입 경로** — 공공 데이터가 부정확할 수 있으므로, 사용자가 소화 체감을 직접
  변경하면 그 선택이 실측 지방량을 대체합니다. 더 무거운 쪽으로 바꾼 사용자의 판단을
  시스템이 무시하는 것은 안전 측면에서 잘못된 방향이기 때문입니다.

**"사용자는 자기가 먹은 음식의 지방량을 모른다"**

타이머는 지방량으로 계산하지만 사용자에게 "지방 몇 g 드셨나요?"라고 물을 수는 없습니다.
그래서 즐겨찾기 등록 시에는 **소화 체감을 세 단계**로만 고르게 하고, 계산 시점에
그램수로 환산합니다.

| 사용자 선택 | 환산값 | 결과 구간 |
|---|---|---|
| 가벼움 | 5g | 2시간 |
| 보통 | 15g | 3시간 |
| 무거움 | 30g | 4시간 |

환산값은 각 구간의 **안쪽에 배치**해, 사용자의 체감이 세 단계 수준에서만 맞으면 결과가
흔들리지 않도록 했습니다. 값의 우선순위는 다음과 같습니다.

```
1순위  AI 자동매칭으로 얻은 식약처 DB의 실측 지방량
2순위  사용자가 고른 소화 체감 → 환산값
```

기본적으로는 실측값을 사용하고, 실측값을 얻지 못했을 때 체감 환산값으로 대체합니다.
다만 사용자가 소화 체감을 **명시적으로 변경한 경우**에는 그 선택이 실측값을 대체합니다.

### 왜 지방인가

**① 위는 부피가 아니라 열량을 기준으로 비웁니다.** 초기 30분 이후 십이지장으로의
에너지 전달 속도는 평균 2.5 kcal/min으로 수렴합니다(Hunt et al., 1985). 지방은 1g당
9kcal로 탄수화물·단백질(4kcal)의 두 배 이상이므로, **같은 1g을 더 먹었을 때 위 체류
시간을 가장 많이 늘리는 영양소**입니다.

**② 지방은 증상을 느끼는 민감도까지 올립니다.** 열량 밀도는 식도 산 노출의 정도를,
식이의 지방 비율은 역류 증상 빈도를 각각 독립적으로 결정합니다(Fox et al., 2007).
십이지장에 지방이 도달하면 속쓰림 인지가 강화되는 기전도 확인되었습니다(Meyer et
al., 2001).

즉 지방은 **객관적 지표와 주관적 지표를 동시에 건드리는 유일한 영양소**이며, 그래서
부피나 총 칼로리가 아닌 지방을 단일 지표로 선택했습니다.

### 왜 10g과 25g인가

논문에 특정 그램 수 임계값은 존재하지 않습니다. 대신 **"평범한 한 끼가 몇 g인가"**를
서로 독립적인 세 기준으로 확인해, 그 범위의 경계로 설정했습니다.

| 기준 | 한 끼 지방 "보통" 범위 |
|---|---|
| 2025 한국인 영양소 섭취기준 (지방 에너지 15~30%) | 11 ~ 22g |
| 국민건강영양조사 실제 섭취 (1일 46g ÷ 3끼) | 약 15g |
| 위 배출 연구가 "저지방식"으로 정의한 값 | 9.2g |

- **한국인 영양소 섭취기준**: 2,000kcal 기준 → 지방 300~600kcal(에너지적정비율 15~30%)
  → 하루 33~67g → 한 끼 11~22g으로 환산.
- **국민건강영양조사**: 2016~2017년 조사를 분석한 송수진·심재은(2019)에 따르면 한국
  성인 1일 총 지방 섭취량은 약 46g(지방 에너지 비율 21%) → 한 끼 약 15g.
- **위 배출 연구**: Stacher 등(1991)이 건강한 남성 12명을 대상으로 저지방식(9.2g)과
  고지방식(37.9g)의 위 배출 속도를 신티그래피로 비교한 실험에서 정의한 "저지방식" 값.

**10g**은 세 기준 모두에서 보통보다 가벼운 쪽, **25g**은 모두에서 보통을 넘어선 쪽입니다.
두 숫자는 의학적으로 위험한 선이 아니라 평범한 한 끼의 앞뒤 경계이며, 이 경계 자체가
갖는 근본적인 한계는 [알려진 한계](#알려진-한계)에 따로 설명합니다.

## AI 음식 자동매칭

식약처 식품영양성분DB는 **100g 기준** 값을 제공하지만 사용자는 "1인분"을 먹습니다.
이 간극을 메우기 위해 Claude API를 두 지점에서만 제한적으로 사용합니다.

```
검색어 입력
   ↓
식약처 API 조회 (관련도순 상위 15개)
   ↓
이름 완전일치 항목 추출
   ↓
   ├─ 완전일치 1개 이상 ─→ 칼로리 중앙값에 가장 가까운 항목 선택   [순수 코드]
   │                        (동률이면 높은 쪽 — 과소평가 방지)
   │
   └─ 완전일치 0개 ──────→ 상위 10개 중 Claude가 후보 선택         [AI ①]
                             실패 시 관련도순 1위로 폴백
   ↓
1인분 그램수 추정 — Claude 3회 병렬 호출 → 중앙값                  [AI ②]
   실패 시 100g 기준으로 폴백 + 사용자에게 배지로 고지
   ↓
그램수 ÷ 100 × (100g당 칼로리·지방) = 최종값                        [순수 코드]
```

완전일치 후보 중 가공식품 비율이 **80% 이상**인 표준화 제품(라면, 과자 등)은 포장에
표기된 1회 제공량이 아니라 사람들이 실제로 한 번에 먹는 양을, **Claude API의 웹 검색
도구**로 조회한 뒤 그 결과를 근거로 추정하는 별도 경로를 탑니다.

그램수 추정에 3회 병렬 호출 후 중앙값을 쓰는 것은 **자기일관성(self-consistency)**
기법으로, 단일 호출의 편차를 줄이기 위한 것입니다. AI 호출이 실패해도 예외를 던지지
않고 폴백으로 이어져 **검색 자체는 절대 중단되지 않습니다.**

## 설계 원칙 — AI는 값을 만들 수 없다

**AI(Claude)는 이 앱에서 정확히 두 번만 관여합니다**: 완전일치가 없을 때 후보 중
하나를 고르는 것, 그리고 1인분 그램수를 추정하는 것. 칼로리·지방 수치 자체는 100%
식약처 데이터베이스에서만 나오고, 최종 곱셈도 코드가 계산합니다.

이 제약은 프롬프트로 "값을 만들지 마라"고 부탁해서 지켜지는 게 아니라, Claude API에
전달하는 **도구(tool) 스키마 자체에 칼로리·지방 필드가 없도록 만들어 구조적으로
막았습니다**:

- 후보 선택 도구(`select_food`)는 정수형 `index` 하나만 반환할 수 있습니다 — 이름·
  칼로리·지방을 담을 자리가 스키마에 아예 없습니다.
- 그램수 추정 도구(`estimate_serving`)는 숫자형 `grams` 하나만 반환할 수 있습니다.

AI 응답에 실수로 영양성분 숫자가 섞여 들어올 방법 자체가 없다는 뜻이며, 이 구조 덕분에
"AI가 잘못된 값을 만들어냈다"는 유형의 오류는 설계상 발생할 수 없습니다.

모든 엔티티는 `user_id` 외래키로 소유자를 구분해 계정별 데이터를 분리합니다.

**왜 앱이 외부 API를 직접 부르지 않는가.** 식약처·Claude API를 쓰려면 인증 키가
필요합니다. 그 키를 앱 안에 넣으면 배포 후 회수할 수 없고, 리버스 엔지니어링으로
추출될 위험도 있습니다. 그래서 이 키들은 전부 서버에만 두고 앱은 서버하고만
통신하도록 설계했습니다. 키를 바꿔야 할 일이 생겨도 앱을 다시 심사받을 필요가
없습니다.

유일한 예외는 카카오 로그인입니다. 카카오 네이티브 로그인은 카카오톡 앱을 거쳐야
해서 토큰 발급 자체는 iOS SDK가 직접 처리합니다. 다만 그 토큰이 진짜인지는 서버가
다시 카카오 서버에 확인합니다 — 가짜 토큰으로 다른 사람 계정에 접근하는 것을 막기
위해서입니다.

상세한 API 명세와 데이터 흐름, ERD는 `ARCHITECTURE.md`를 참고해 주세요.

## 다른 계산 기능 — BMR·러닝 소모 칼로리

### BMR / 목표 칼로리 — `BMRCalculator.swift`

**Mifflin-St Jeor Equation (1990)**

```
남성: BMR = 10 × 체중(kg) + 6.25 × 키(cm) - 5 × 나이 + 5
여성: BMR = 10 × 체중(kg) + 6.25 × 키(cm) - 5 × 나이 - 161
```

- 유지 칼로리(TDEE) = BMR × 활동계수
  (거의 안 움직임 1.2 / 가벼운 활동 1.375 / 보통 활동 1.55 / 활발한 활동 1.725)
- 증량 목표 = TDEE + 400 kcal

활동계수는 Harris-Benedict 활동계수 체계에서 통용되는 값입니다. 단일 원 논문이
있는 게 아니라 여러 임상 영양 문헌과 계산기에서 관행적으로 쓰이는 근사값이며,
개인차가 커 정밀한 추정에는 한계가 있습니다. Mifflin-St Jeor 원 논문(1990) 자체에는
활동계수가 포함되어 있지 않으며, 활동계수는 별도로 통용되는 값을 가져와 곱하는
방식입니다.

체중 0.5kg 증가에는 약 3,500 kcal의 잉여 열량이 필요하며, 국내 의료기관에서는
증량 시 하루 500 kcal 내외를 추가하도록 안내합니다. 본 앱은 이보다 보수적인
400 kcal를 적용해 주당 약 0.4kg의 완만한 증가를 목표로 했습니다.

### 러닝 소모 칼로리 — `RunAPIService.swift`

```
소모 칼로리 = MET × 체중(kg) × 시간(h)
```

속도 구간별 MET 값은 **2024 Adult Compendium of Physical Activities**의 달리기
항목을 참고했으며, 각 구간의 **하한 속도에 해당하는 값**을 사용했습니다.

| 속도 (km/h) | MET | | 속도 (km/h) | MET |
|---|---|---|---|---|
| < 8.05 | 6.5 | | < 12.87 | 11.0 |
| < 9.66 | 8.5 | | < 14.48 | 12.0 |
| < 10.78 | 9.3 | | < 16.09 | 13.0 |
| < 11.27 | 10.5 | | ≥ 16.09 | 14.8 |

체중은 사용자가 입력한 값을 사용하며, 입력되지 않은 경우 부정확한 값이 기록에 남지
않도록 저장을 차단하고 입력을 안내합니다.

## 겪은 문제와 해결

### 외부 API 타임아웃 부재로 인한 서버 전체 장애 (2026-08-09)

식약처 API를 호출하는 코드에 타임아웃이 전혀 설정되어 있지 않았습니다. 외부 서버가
응답을 늦게 주거나 주지 않으면 그 요청이 쓰던 커넥션이 반납되지 않고 쌓였고, 이
호출이 요청을 처리하는 스레드 안에서 이루어지다 보니 스레드까지 함께 묶였습니다.
오래 가동될수록 이런 상황이 조금씩 쌓이다가, 어느 순간 커넥션 풀이 완전히
고갈되면서 **특정 음식이 아니라 검색 기능 전체가 멈추는 장애**로 이어졌습니다.

어느 단계에서 멈추는지 알 수 없어 각 구간의 시작·종료를 로그로 남겼고, 시작은
찍히는데 완료가 찍히지 않는 지점을 찾아 식약처 API 호출로 원인을 좁혔습니다.
연결 5초 / 읽기 15초로 타임아웃을 추가해 커넥션이 쌓이는 근본 원인을 막았습니다.
다음 날 같은 패턴(타임아웃 미설정)이 카카오·Apple 로그인과 회원 탈퇴 호출에도
남아 있는 것을 확인해 동일한 기준을 적용했습니다.

### App Store Guideline 1.4.1 반려 대응

1차 심사에서 "BMR 등 건강/의료 계산 결과를 출처 인용 없이 보여준다"는 이유로
반려되었습니다. 건강 계산 결과가 실제로 표시되는 화면(내 정보, 러닝 상세,
식단·타이머) 네 곳에 계산 근거 화면 진입점을 추가하고, BMR·MET·소화 타이머 각각의
근거 논문을 앱 안에서 바로 확인할 수 있게 했습니다. 이 작업 중 기존 자료에 잘못
기재되어 있던 참고문헌 PMID 하나(무관한 논문을 가리키던 오기)도 함께 발견해
정정했습니다.

## 알려진 한계

### 정확한 위 배출 시간은 측정할 수 없다는 근본적 한계

이 앱의 2/3/4시간 임계값은 학회 권고(취침 전 2~3시간)와 위 배출 연구(고형식 90%가
4시간 이내 배출)를 근거로 한 값이지, **사용자 개인의 실제 위 배출 시간을 측정한
값이 아닙니다.** 실제 위 배출 시간은 신티그래피 같은 의료기기 없이는 측정할 수
없고, 이 앱은 의료기기가 아닙니다.

이 한계는 감추지 않고 명시합니다 — 대회 심사에서도 동일한 지점을 지적받았습니다.
개선 방향으로는 사용자가 먹은 음식을 사진으로 찍어 조리 상태·양을 더 정확히
추정하는 입력 방식 등을 검토했으나, 대회 종료 후 운영을 중단하며 착수하지는
못했습니다.

### 공공 데이터의 커버리지·품질 편차

식약처 식품영양성분DB를 직접 호출해 검증한 결과, 두 유형의 한계를 확인했습니다.

| 유형 | 사례 | 내용 |
|---|---|---|
| 항목 부족 | 곱창 | 전체 594건 중 이름 완전일치가 1건뿐이라 대안 없이 그 값을 사용 |
| 조리 상태 혼재 | 쌀국수 | 건면·조리식·즉석제품이 섞여 중앙값이 대표성을 잃음 |

쌀국수의 경우 건면 기준 값이 선택되어 지방이 실제보다 낮게 산출되며, 이는 **대기
시간이 실제보다 짧게 안내되는 방향**이라 건강 기능에서는 더 주의가 필요한
오차입니다. 사용자가 소화 체감을 직접 변경해 실측값을 덮어쓸 수 있는 경로로
대응했습니다.

> 영양성분 값 자체를 AI 추정으로 대체하는 방향은 채택하지 않았습니다. 출처를
> 제시할 수 없는 값은 건강 관련 기능에서 근거가 될 수 없으며, "AI는 값을
> 생성하지 않는다"는 설계 원칙과도 충돌하기 때문입니다.

### 인증 방식

세션 기반 인증을 사용했으며, 서버 재시작 시 세션이 초기화되는 구조였습니다.
